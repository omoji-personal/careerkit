# CareerKit hardening and release audit - 2026-08-20

Multi-lens, full-repository review of the CLI, scoring and storage invariants,
network boundary, application contract, packaging, setup/update paths,
documentation, generated guide, and CI. The clean reference was `main` at
`15a150125a2b082dd892c83ba622d50054bc092c` with 388 tests. Findings were
reproduced before repair, covered by regression tests, and then exercised
together against synthetic isolated state. No live sourcing run, application,
message, or private-data mutation was part of this audit.

## Release verdict

The reviewed source is ready for a branch checkpoint. CareerKit remains
intentionally clone-only: its skills, operating contract, setup workflow, and
private-state layout are part of the product, so a partial wheel or PyPI console
install is not a supported deployment. The project-owned virtual environment
has been migrated through `./setup.sh`; public deployment still requires an
authorized push and green GitHub Actions on the exact commit.

## Remaining deployment gates

These are operational or repository-administration boundaries, not hidden by a
green local suite:

1. Push the reviewed commit only with explicit authorization, then require the
   complete GitHub Actions matrix to pass on that exact SHA before merging.
2. Enable GitHub secret scanning, push protection, Dependabot alerts/security
   updates, private vulnerability reporting, and branch protection or rulesets.
   They were observed disabled and require repository-admin action.
3. The private consumer copy exposed two legacy impossible compensation bands.
   The new repair sequence cleared and re-derived them successfully on the copy;
   the live database was deliberately not changed. Review its backup, then run
   `consistency --repair`, `rescore`, and `report` before relying on those bands.
4. Keep the JobSpy feed inactive until an upstream dependency graph supports a
   security-fixed Markdown converter; the other feeds remain available.
5. Continue distributing CareerKit as a complete source checkout. A future
   package release needs a deliberate resource and user-data-home design rather
   than reintroducing the removed partial console install.

Passing tests cannot prove the absence of every defect. This checkpoint means
the confirmed findings above are repaired, their reproduced failure modes are
covered, and the local release artifacts agree; it does not convert an unpushed
branch into a public release.
