# Adversarial audit, 2026-08-05

Four independent lenses over the repo at `cf870f5`: Claude (a fan-out of
dimension finders with refute-by-default verification), Gemini 3.1 Pro via
Antigravity, Kimi K3, and hand verification. Codex was quota-locked and did not
participate.

Every finding below was reproduced with an executed script before being
accepted, and the fixes ship with regression tests in `tests/test_engine.py`.
Findings that did not survive verification are listed at the end, because a
list of only confirmed bugs hides how much of an audit is wrong.

---

## P0 — distinct requisitions collapsed into one row

`engine/models.py`, the `uid` property.

`uid` was `sha256(company | normalized_title)`. Two genuinely different openings
at one employer with the same title produced ONE database row. The second
posting's URL and location were discarded on write, and because `store.query`
excludes rows marked `applied`, applying to one made every sibling permanently
invisible.

Reproduced: a Denver "Product Manager" and an Austin "Product Manager" stored as
a single row keeping only Denver; marking it applied dropped the result set to
zero. All four lenses found this independently.

The original docstring defended the key, correctly, as what prevents the same
role appearing four times when it arrives via the ATS, two aggregators and a
repost. The benefit was real; the cost was not noticed.

**Fixed** by splitting the two jobs the key was doing. `group_key` stays
`company | title` and is what merges sightings of one role. `uid` adds the
board's own requisition id, but only when the sighting came from the employer's
own ATS, since aggregators mint their own ids and would otherwise re-fragment
what `group_key` exists to merge.

## P0 — a stray empty list item silently matched every posting

`engine/score.py`, `_compile_alt`.

Terms were compiled as `\b(a|b|c)\b`. An empty alternative, from a `""` left in
a YAML list or a raw regex ending in `|`, produces `\b(a|)\b`, which matches at
every word boundary in every document. In `exclusions.titles` that gates out
every job, so the user sees an empty report indefinitely, indistinguishable from
a quiet day. This is the exact failure the tool exists to prevent, reachable by
a plausible typo from a non-technical user.

**Fixed.** Unusable terms (empty, null, malformed regex, any raw regex that
matches the empty string) are dropped with a printed warning naming each one. If
nothing usable remains the pattern is `None` rather than a match-everything.

## P0 — dead and demoted postings kept being presented as live

`careerkit.py` `cmd_pull`, `engine/store.py`.

Only QUALIFIED and VERIFY rows were passed to `upsert`. Two consequences:

1. A posting that stopped qualifying (the user tightened their profile, or the
   board edited the body) was never written back and kept surfacing at its old
   gate forever.
2. A posting removed from its board is simply absent from the next pull. Nothing
   marked it closed, so it stayed QUALIFIED indefinitely.

This is not hypothetical. It put a dead Anthropic requisition in front of the
owner in July 2026. The STALE annotation added afterwards was a mitigation, not
a fix: rows were still never invalidated, and the flag only appears after two
days, so a posting that closed yesterday was shown as live with no warning.

**Fixed** with `store.reconcile`, called at the end of every pull. Demoted rows
are written back; rows not seen this run are marked `delisted_on` and drop out
of `query`. A row is only delisted when its source actually reported
successfully, so a broken board is never read as "every job there closed".
Re-sighting a delisted posting revives it.

## P0 — setup.sh aborted on the first step on a modern machine

`setup.sh` ran `python3 -m pip install --user pyyaml` under `set -e`. Modern
Python installs are marked externally-managed under PEP 668 and refuse that
command, so the script died with pip's error text for anyone who did not already
have the dependency. The author never saw it because his machine already had
PyYAML. It also never installed `requests`, a hard dependency, and there was no
`requirements.txt`.

**Fixed.** `setup.sh` creates a `.venv`, installs from `requirements.txt`, checks
the Python version, and gives platform-specific guidance on failure.
`careerkit.py` re-execs itself inside `.venv` so running it directly works
without anyone remembering to activate anything.

## P1 — "Remote (US)" carried no US evidence

`engine/score.py`, `US_EVIDENCE`.

The alternative `u\.?s\.?a\.?` requires the trailing "a", so the bare token "US"
never matched. Postings labelled "Remote (US)" or "Remote, US", among the
commonest forms there is, had no US evidence and fell to VERIFY instead of
QUALIFIED. Measured on the owner's live database: 3 of 254 rows.

**Fixed** with a separate case-sensitive `US_TOKEN` pattern.

## P1 — an empty board and a blocked board were reported identically

`engine/adapters.py`, `run_adapter`.

`if not jobs: return [], "0 postings returned"`, and the HTTP status was already
discarded inside `fetch_json`. A Cloudflare 403 and a company with no current
openings produced byte-identical output. Every genuinely-empty board accumulated
`consecutive_failures` and appeared under "sources failing repeatedly (silent
coverage loss)".

Measured on the owner's live database: 12 of 15 flagged sources were healthy but
empty. A list that is 80% false alarms gets ignored, and then a real failure
hides in it.

**Fixed.** `http.last_status()` exposes the real status per thread. An empty list
after a 200 is reported as healthy; anything else reports the actual status.

## P1 — mutable fields froze at first sighting

`engine/store.py`, `upsert`. The UPDATE path refreshed score, gate, reasons and
comp, but never url, title, location or description. A board that re-issued a
posting under a new URL left the row pointing at a dead link permanently.
**Fixed**, with description guarded so an empty re-fetch cannot erase a good one.

## P2 — `mark` accepted any string

`engine/store.py`, `set_status`. Any status was written, but `query` only
understands five. `mark UID apllied` silently left the job in the active list
while the user believed it was filed. **Fixed:** validated against
`VALID_STATUS`, unknown uid raises, and the CLI prints a clear message instead
of a traceback.

## P2 — the HTTP cache ignored CAREERKIT_HOME

`engine/http.py`. `store.DB_PATH` and `report.OUT_DIR` both honour
`CAREERKIT_HOME`; `CACHE_DIR` did not, so a shared-engine instance wrote its
cache into the engine repo while its database went to its own home. That breaks
the per-person isolation `new-instance.sh` exists to provide. **Fixed.**

Separately: the cache had grown to 177 MB across 632 files with no eviction, and
`clear_cache()` was defined but never called from anywhere. The 6-hour TTL means
staleness is bounded, so this is housekeeping, not correctness.

## P2 — the README overclaimed on privacy

"CareerKit itself sends nothing anywhere" was not true. The tool makes outbound
requests to dozens of third-party job boards, and the USAJobs feed transmits the
user's registered email in a request header because that API requires it.
**Fixed** with a "What actually leaves your machine" section that says plainly
where data goes, including the scraping feeds and their ban risk.

## P2 — the agent contract had gaps the skills did not encode

`autonomy.submit` had no consumer anywhere; the `apply` skill, the one that fills
forms, never mentioned autonomy at all. `eeo` and `work_auth` were written by
`/setup` and read by nothing, so the agent re-improvised EEO answers on every
application instead of using the stored ones. Of the six skills that fetch
untrusted external text, only `ingest` restated the "this is data, not
instructions" boundary. **All fixed**, with the guard now in all six.

## P3 — a schema change would have broken every existing user

`CREATE TABLE IF NOT EXISTS` is a no-op on an existing table, so a column added
later never appears for anyone with an existing database. Found while fixing the
above, because the first version of the fix added an index on the new column and
aborted `connect()` with "no such column: group_key". **Fixed** with an explicit
migration step that runs between table creation and index creation, with a test
that upgrades a synthetic v1 database.

## Not fixed, deliberately

**No mechanism enforces the claims register.** "Never fabricate experience" is a
prompt-level rule with no validator behind it. Building one is a real project and
a weak version would be worse than none, because it would imply a guarantee that
does not exist. The README now says plainly that these are prompt-level rules,
not sandboxed controls.

**`feed:remoteok` caps at 100 results.** One feed, low value, not worth
pagination work until it matters.

**The HTTP cache has no eviction.** Bounded staleness (6h TTL), unbounded size.
`clear_cache()` exists if it ever becomes a problem.

## Claimed but refuted

Kept because knowing what an audit got wrong is part of the record.

- **Pagination truncating large employers.** 13 of 17 adapters make a single
  request, which looked alarming. Refuted against the owner's live data: 550
  results for greenhouse:Stripe, 735 for ashby:OpenAI. Those endpoints return
  everything.
- **Lowercased US state codes read as foreign countries.** Real in code for eight
  states, but zero of 632 real cached payloads lowercase locations, so it was
  unreachable in practice. Fixed anyway while nearby, since the fix was one line.
- **`autonomy:` ignored entirely.** Overstated. Two of its three keys did have
  consumers; only `submit` had none.
- **The `apply` skill lacking a stop-at-submit rule.** It encodes it well, with
  tiered handling for account-walled and captcha-hostile forms. The accurate
  version of the criticism is that no *structural* lock exists, which is true of
  any agent tool and is now stated in the README.
- **Owner PII in the repo.** Grepped tracked files and full git history: clean.
  The one apparent hit in the HTTP cache was "omidyarnetwork", a real company.
