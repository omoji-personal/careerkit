# Adversarial review — 2026-08-11

Four independent lenses over the per-employer rules added this day, plus the
engine paths they touch. Baseline 339 tests green; ended at 369.

Panel: Claude (this repo's author), agy, codex, kimi. Every external finding
was treated as a lead and verified against the code or the live corpus before
being acted on. What was refuted is recorded here too, because a review whose
false positives go unrecorded reads as more authoritative than it was.

**No P0s were found by any lens.**

## What changed this day

- `exclusions.company_floors: {Employer: N}` — an employer worth watching but
  effectively unreachable (an application cap already spent, a recruiter-only
  route) surfaces only a standout req. A floor, not a ban.
- `exclusions.companies: [Employer]` — an outright block. This key had been
  declared in `PROFILE_SCHEMA` since the schema was written and read by nothing,
  so setting it produced no warning and no effect.
- Both applied in a thin `score()` wrapper around `_score_uncapped`.

## Confirmed and fixed

| # | Lens | Defect |
|---|---|---|
| 1 | Claude | The floor, written at the natural end of `score()`, held for none of that function's ~12 early returns. 46 rows surfaced under a floor of 75 on the live database, all out of the thin-body domain branch. Moved outside the scorer. |
| 2 | Claude | `remote_flag` was written by the INSERT and by nothing else, so rows predating the column kept NULL forever and every `rescore` re-judged them as onsite. Nine live rows demoted in one rescore. |
| 3 | Claude | Healing it with a plain `COALESCE` let a `False` erase a `True`. Sources disagree about what `False` means: `adapters.py:118` writes None when the board said nothing, `aggregators.py:102/:321/:512` write `bool(payload.get("remote"))`. Four uids in the live database are seen from two sources at once. The heal is now one-way. |
| 4 | Claude | A blank entry in `exclusions.companies` put `""` in the set, matching every job with a blank company. Same failure `_compile_alt` already has a regression test for, in a different shape. |
| 5 | agy + codex | The floor's reason interpolated the raw company name ahead of the colon. The report breakdown and `audit` both key on `reasons[0].split(":")[0]`, so one employer spelled two ways split into two buckets — and an earlier wording split on the score, giving eighteen. |
| 6 | codex | **The systematic one.** `store.upsert`'s UPDATE path writes a shorter column list than the INSERT, and three more fields `score()` reads were missing: `employer_tier` (+6/+3, enough to cross a floor), `rails_exempt` (waives the location rails), `department` (feeds the domain rail), plus `comp_text`. |

### The lesson worth keeping from #6

An invariant test named `test_pull_and_rescore_agree_on_every_field_the_scorer_reads`
already existed, written after `remote_flag` shipped this exact bug. It could
not catch these three, because it upserts each posting **once** — so it only
ever exercised the INSERT path, which writes every column. The drift lives in
the UPDATE path.

The 2026-08-10 lesson was "an invariant test only covers the fields its fixture
uses". This is the same lesson one layer deeper: **it only covers the code paths
its fixture walks.** Extended to re-sight a stored row; confirmed RED at
41-on-fetch versus 35-from-database before the fix.

## Refuted — recorded so they are not re-litigated

- **agy:** `_company_floors` raises a bare `AttributeError` when `company_floors`
  is written as a YAML list. It does not. The schema type check raises
  `ProfileError: 'exclusions.company_floors' must be dict, got list` first,
  naming the key and the type. A test now locks that in.
- **agy:** the employer-block reason splits breakdown buckets. It does not; it
  already places the company after the colon. Only the floor had this defect.

## Confirmed, no live exposure

- **agy:** deactivating an **aggregator feed** strands its rows permanently.
  Feed sources are not in `ATS_SOURCES`, so the orphan rule cannot reach them
  and their `misses` never increment. Mechanism verified in code; all three
  inactive feeds in the live database have zero undelisted rows.

## Open, deliberately not fixed here

- **codex:** a demoted row refreshes only its verdict. `reconcile` receives
  `(score, gate, reasons)` and not the `Job`, so the field heals in `upsert`
  never reach rows that were demoted. This is the residual: a `rescore` run
  immediately after a `pull` changed 26–51 verdicts before this work and now
  changes 4, with the second rescore changing 0 (converged and idempotent).
  Closing it means giving `reconcile` the Job, or letting `upsert` run in an
  update-only mode for demotions.
- **codex:** among duplicate sightings that are ALL demoted, "best gate wins" is
  last-write-wins, so a foreign-located copy can overwrite a clean one.
- **codex:** `seen_count` and `sightings.seen_on` do not advance for demoted
  rows, so their provenance and frequency data go stale.
- **agy:** `reconcile`'s `status NOT IN ('applied','rejected','ignored')` guard
  means an `ignored` row never accrues misses; un-ignoring it later can surface
  a posting that died while it was hidden.
- **Pre-existing, outside this change set:** `applied.py:62 _title_overlap`
  divides shared words by the SHORTER title's word count, so a three-word title
  sharing two common words scores 67% and trips the ≥0.6 "you were rejected for
  X at this employer" warning. On the live database it fired on the highest
  scoring role in the pipeline. It errs toward telling the user to skip a good
  role, which is the expensive direction.

## Panel mechanics worth remembering

- **codex is unreachable through `dispatch`.** It fails inside the sandbox-exec
  confinement with `invalid peer certificate: UnknownIssuer` and runs fine
  outside it. The confinement was NOT weakened; the review ran against the same
  staged public directory directly, which is sound only because this repo is
  public. The 2026-08-06 note that codex is blocked still holds, with a new
  symptom.
- `-m gpt-5.3-codex-max` is rejected on a ChatGPT-account login
  ("not supported when using Codex with a ChatGPT account").
- **The FACTS sheet is load-bearing.** The 2026-08-06 review produced three
  false P0s from a thin evidence sheet. This one stated the gate vocabulary, the
  storage consequences of EXCLUDED vs SLOT-BLOCKED, what was already tested, and
  which decisions were deliberate — and the false-positive rate fell to two out
  of fifteen external findings.
